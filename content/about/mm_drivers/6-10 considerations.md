Been contemplating the 10 first-order Outcomes we have on mm_drivers/index.md (What Drives Us). Although we have these sorted into four capacities what I keep coming back to is that 10 is maybe too heavy. Thinking what we have as four capacities are the first-order outcomes. Then we redefine the 10 we have sorted into these as forces, agents, levers, drivers or something that can be manipulated and managed to achieve the capacities (redefined as outcomes).

Thought for a few seconds

I think this is a very good instinct.

The current structure works intellectually, but **10 first-order outcomes may be too many for the reader-facing “What Drives Us” page**. Ten asks the reader to hold too much at the top level.

Your proposed shift is stronger:

```
Four capacities = first-order outcomesThe ten current items = enabling capacities / levers / practices / drivers that strengthen those outcomes
```

That gives the page a cleaner hierarchy.

## Why this feels better

The four current buckets already read like the real first-order outcomes:

1. **Seeing systems more clearly**
2. **Participating inside systems with more awareness**
3. **Building, tuning, measuring, and leading systems with more conscience**
4. **Making the invisible easier to discuss**

Those are bigger, more memorable, and more visitor-facing.

The ten current “outcomes” are more granular. They describe what helps those four capacities become possible.

For example:

**Seeing systems more clearly** is the outcome.  
**System sight, outcome literacy, metric skepticism, reduced false certainty** are the enabling capacities that make it real.

That feels right.

## The naming problem

I would avoid calling the ten items **forces**, **agents**, or **levers**.

**Forces** may imply they act on their own.  
**Agents** may confuse with people or AI agents.  
**Levers** feels too mechanical and managerial.  
**Drivers** is decent, but you already have “What Drives Us,” so it may create slight ambiguity.

My strongest recommendation is:

> **supporting capacities**

or:

> **enabling capacities**

I slightly prefer **supporting capacities** for the public page because it feels human and less technical.

A clean structure would be:

```
First-order outcomes  → four core capacities MNKY Math is trying to strengthenSupporting capacities  → the more specific skills, lenses, and habits that help produce those outcomes
```

## Revised framing

Instead of:

```
## First-order outcomesThese are the immediate capacities MNKY Math is trying to strengthen.
```

You could say:

```
## First-order outcomesThese are the four core capacities MNKY Math is trying to strengthen.They describe the kind of participation this work is oriented toward: clearer seeing, more conscious participation, more careful building, and shared language for what systems usually keep hidden.
```

Then under each expander:

```
_Core supporting capacities in this outcome:_
```

Instead of:

```
_Core outcomes in this family:_
```

That one phrase change may solve a lot.

## Updated hierarchy

```
## First-order outcomesThese are the four core capacities MNKY Math is trying to strengthen.1. Seeing systems more clearly.2. Participating inside systems with more awareness.3. Building, tuning, measuring, and leading systems with more conscience.4. Making the invisible easier to discuss.These outcomes are supported by more specific capacities, such as system sight, outcome literacy, agency recovery, design conscience, tradeoff visibility, and cleaner language.Those supporting capacities are not separate goals competing for attention.They are the ways these larger outcomes become visible, usable, and repeatable.
```

Then each callout becomes:

```
> [!info]- Seeing systems more clearly> ...> _Supporting capacities in this outcome:_> - [[mm_system_sight|System sight]]> - [[mm_outcome_literacy|Outcome literacy]]> - [[mm_metric_skepticism|Metric skepticism without metric rejection]]> - [[mm_reduced_false_certainty|Reduced false certainty]]
```

## What happens to the individual pages?

I would **keep the individual pages**.

But I would reframe them as:

```
supporting capacity pages
```

not first-order outcome pages.

They still function exactly as you intended:

- tag explanation pages
- hover preview destinations
- graph nodes
- cross-linking surfaces
- orientation nodes
- backlinks into Foundations, Archive, Tools, and Neighborhood

The content template still works. You may only need to change the frontmatter/tag language from:

```
tags:  - outcome  - first-order-outcome
```

to something like:

```
tags:  - supporting-capacity  - outcome-support
```

Or, if you want to preserve the original architecture for now:

```
tags:  - outcome  - supporting-capacity
```

I would avoid overhauling too much until you feel the public-facing language is stable.

## This also improves the second-order model

The hierarchy becomes cleaner:

```
Supporting capacities  → strengthen first-order outcomes  → create conditions for second-order outcomes  → which can become system inputs that reinforce the first-order outcomes
```

Example:

```
System sight + outcome literacy  → clearer seeing  → better meetings  → meetings become feedback loops  → feedback loops strengthen system sight and outcome literacy
```

That is much cleaner than treating all ten plus the second-order outcomes as one large outcome landscape.

## My recommended terminology

Use:

```
First-order outcomesSupporting capacitiesSecond-order outcomesCollateral and emotional outcomes
```

That is clear, durable, and not too jargon-heavy.

If you want slightly more MNKY Math flavor:

```
Core outcomesSupporting capacitiesSystem-level outcomesHuman-residue outcomes
```

But I would stay plainer for now.

## Bottom line

Yes — I would make the four buckets the actual **first-order outcomes**.

The ten current items should become **supporting capacities**.

That reduces cognitive load, makes the page more elegant, and actually clarifies the system:

> MNKY Math is trying to produce four core shifts.  
> The supporting capacities are how those shifts become possible.
